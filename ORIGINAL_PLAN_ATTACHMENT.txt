
🟢 المرحلة 1: تثبيت الأساس (5,000 – 8,000 سطر)
الهدف: نواة مستقرة تقدر تبني عليها.

□ GDT + TSS محترم (مش بس اللي Limine بيعمله)
□ IDT كامل لكل الـ 256 vector
□ Exception Handlers (Page Fault, GPF, Double Fault) — دي هتنقذك كتير
□ PIC → APIC (عشان تدعم SMP بعدين)
□ PIT / HPET للتوقيت الدقيق
□ Serial Debug Console قوية (log levels)
□ Panic Screen لما يحصل crash
□ Memory: VMM (Virtual Memory Manager) — Paging للـ Kernel
□ Kernel Heap حقيقي (Slab / Buddy Allocator)
اللي هيشتغل: نواة مستقرة، بتكتشف الأخطاء، وبتديك logs واضحة.

🟢 المرحلة 2: User Mode + Processes (15,000 – 25,000 سطر)
الهدف: تفصل الكيرنل عن التطبيقات. ده أهم تحول في المشروع كله.

□ Ring 3 setup (GDT entries + sysret/iretq)
□ Syscall Interface (int 0x80 أو syscall/sysret)
□ Process structure (PCB, PID, state)
□ Context Switch حقيقي (kernel threads + user threads)
□ fork() / exec() / wait() / exit()
□ ELF64 Loader (يشغل ملفات تنفيذية)
□ Virtual Memory per process (كل process له address space)
□ Copy-on-Write (اختياري بس مفيد)
□ Signals بسيطة (SIGKILL, SIGSEGV, SIGINT)
□ Scheduler محترم (Round-Robin + Priorities + Sleep/Wake)
اللي هيشتغل: تشغل برنامج user-mode بسيط، وتعمل fork/exec، وكل process معزول.

⚠️ نصيحة: هنا ابدأ تكتب libc مصغرة بالتوازي.

🟢 المرحلة 3: نظام الملفات (15,000 – 25,000 سطر)
الهدف: تخزين حقيقي وتنظيم.

□ VFS Layer (يعزل الكيرنل عن نظام الملفات الفعلي)
□ Block Device Layer (يخلي الأقراص كلها تشتغل بنفس الواجهة)
□ FAT32 Driver (سهل + portable + يقرأ فلاشات)
□ ext2 Driver (احترافي وبيتعلم منه)
□ File Descriptors (open/read/write/close/lseek)
□ Directories (opendir/readdir/mkdir/rmdir)
□ Mount Points (/, /mnt, /dev, /proc)
□ Block Cache (يسرّع القراءة)
□ /dev filesystem (للأجهزة)
□ /proc filesystem (معلومات النظام)
اللي هيشتغل: تقرأ وتكتب ملفات على قرص حقيقي، وتعمل مجلدات، وتـ mount.

🟢 المرحلة 4: Userland + Shell + libc (20,000 – 30,000 سطر)
الهدف: بيئة استخدام فعلية.

□ libc مصغرة: string.h, stdio.h, stdlib.h, unistd.h, fcntl.h
□ Shell حقيقي: pipes, redirection, background jobs, variables
□ Coreutils: ls, cat, cp, mv, rm, mkdir, echo, ps, kill, top, grep, wc
□ Text Editor: nano-like بسيط
□ Init system: يشغل خدمات عند البدء
□ Package manager بسيط (اختياري)
□ Compiler/Linker: استخدم tcc بدل ما تكتب واحد
□ Terminal emulator (VT100 escape codes)
اللي هيشتغل: بيئة شبيهة بـ Unix، تكتب فيها أوامر، وتشغل برامج.

⚠️ ملاحظة: ممكن تستخدم musl libc أو newlib بدل ما تكتب libc من الصفر. توفير ضخم.

🟢 المرحلة 5: Drivers للأجهزة (20,000 – 40,000 سطر)
الهدف: تشتغل على هاردوير حقيقي.

□ AHCI (SATA) — بدل ATA PIO القديم
□ NVMe — للأقراص الحديثة
□ USB Stack: xHCI + HID (كيبورد + ماوس)
□ PCI/PCIe enumeration
□ ACPI: power off, reboot, sleep
□ Network Drivers:
Intel e1000 / e1000e

VirtIO-Net (لـ QEMU)

Realtek RTL8168/8111

□ Audio: AC'97 أو Intel HDA (اختياري)
□ RTC (الساعة الحقيقية)
اللي هيشتغل: النظام يشتغل على لابتوب/PC حقيقي، مش بس QEMU.

اللي هيشتغل: واجهة تشبه Windows 95/2000 أو Haiku — بسيطة وحلوة.

عايز أبدأ معاك من المرحلة 1 بالتفصيل؟ أقدر أديك خطة أسبوعية وخطوات تنفيذية.

طيب  سوال  كل ده  في الاخر هيبقي في main   واحد  صح
The user is asking: will all this end up in one main file/function? Good question about architecture.

سؤال ممتاز، وده من أهم الأسئلة المعمارية في المشروع كله.

الإجابة المختصرة
لأ، مستحيل. اللي عندك دلوقتي كله في main.c (2000 سطر) ده مقبول كنموذج تعليمي، لكن لو المشروع كبر لـ 300 ألف سطر، main.c واحد = كارثة.

ليه؟
الملف الواحد مش هيتفتح أصلًا — المحرر هيتعلّق.

الـ Compilation هيبقى بطيء جدًا — أي تعديل = إعادة بناء كل حاجة.

مفيش فصل مسؤوليات — كل حاجة بتشوف كل حاجة.

مستحيل يشتغل عليه أكتر من شخص — conflicts كل يوم.

Debugging هيبقى جحيم.

مفيش modularity — مش هتقدر تستبدل جزء أو تختبره لوحده.

الشكل الصح: ملفات كتير + main.c صغير
kmain() في الآخر هيبقى 20-100 سطر بس، بيعمل حاجة واحدة: يستدعي subsystems بالترتيب. زي:

c
void kmain(void) {
    serial_init();
    gdt_init();
    idt_init();
    pmm_init();
    vmm_init();
    heap_init();
    pci_init();
    drivers_init();
    scheduler_init();
    vfs_init();
    net_init();
    gui_init();
    shell_start();
    for (;;) { idle(); }
}
خلاص. كل حاجة تانية في ملفات مستقلة.

القواعد الذهبية للتنظيم
كل subsystem في فولدر — mm, fs, net, drivers, gui, ...

كل ملف .c ليه .h مناظر — التصريحات بس في .h.

مفيش #include "main.h" — كل ملف بيـ include اللي محتاجه بس.

Interfaces واضحة — ملفات subsystems متكلمش بعض مباشرة إلا من خلال APIs معرّفة.

kmain() بيعمل init بس — أي منطق حقيقي في subsystems.

Makefile أو CMake يدير كل حاجة — مش compile يدوي.

Layered architecture:

text
Userland → Syscalls → Kernel Services → Drivers → Hardware
مثال حقيقي: لينكس
لينكس عنده:

~30 مليون سطر

موزعة على ~70,000 ملف

init/main.c عنده بس ~1500 سطر

كل subsystem في مجلد لوحده (mm/, fs/, net/, drivers/, arch/)

يعني حتى لينكس نفسه، "main" صغير جدًا بالنسبة لحجم المشروع.

ليه ده مهم لمشروعك؟
لو مشروعك كبر وانت لسه كله في ملف واحد:

مش هتقدر تكمل بعد 10-20 ألف سطر

هتعيد كتابة كل حاجة لما تكتشف إن التصميم غلط

هتكره المشروع قبل ما توصل للنص

لذلك من أول 5000 سطر، ابدأ قسّم.

نصيحة عملية
دلوقتي فورًا: اقسم main.c لملفات:

pmm.c, vfs.c, net.c, gui.c, shell.c

خلي kmain.c صغير

اعمل Makefile يشوف كل ملفات .c تلقائيًا.

اعمل include/ مشترك للـ headers العامة.

كل ملف ≤ 1000 سطر (لو زاد، قسّمه).
